# 0001. AI 설명 생성과 저장을 분리한다

- 상태: 채택
- 작성: 2026-11-09 (Story 10에서 내린 결정을 나중에 기록)

## 배경

Story 9까지 `POST /products/{id}/generate-description`은 AI가 만든 설명을 응답으로 돌려주기만 했다. 저장 기능이 없어서 설명을 상품 정보로 쓸 수 없었다.

저장을 추가해야 했지만, AI가 쓴 문장을 그대로 믿을 수는 없다. 프롬프트로 "제공되지 않은 사양을 지어내지 말라"고 지시해도, 그대로 지켜진다는 보장은 없다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 생성하면 바로 DB에 저장 | API 하나로 끝나고 단순함 | AI 문장이 검토 없이 상품 정보가 됨 |
| B. 생성(미리보기)과 저장 API를 분리 | 사람이 확인하고 고친 내용만 저장됨 | 요청을 두 번 보내야 함 |
| C. B에 더해 설명 이력까지 관리 | 이전 설명을 다시 볼 수 있음 | 테이블과 API가 늘어나 범위가 커짐 |

## 결정

**B를 선택했다.**

- `POST /products/{id}/generate-description`: AI 초안 생성. DB에 저장하지 않음
- `PUT /products/{id}/description`: 사람이 검토한 설명을 저장

### 이유

A는 처리 과정이 단순하고 깔끔하지만, AI가 만든 설명을 그대로 믿고 DB에 저장하게 된다. AI가 잘못된 내용을 쓰면 그 오류가 상품 정보에 그대로 들어갈 수 있다. 그래서 A보다 번거롭더라도 관리자가 확인한 뒤 저장하는 B를 선택했다. 이 방식이 더 믿을 수 있고, 잘못된 정보가 저장될 가능성도 줄일 수 있다.

C는 B를 더 강화한 방법이지만, 범위와 규모가 예상보다 많이 커지기 때문에 효과적이라고 보기 어렵다. 이력을 남기려면 이력 테이블과 마이그레이션, Entity와 Repository, 이력 조회 API, 상품을 삭제할 때 이력을 어떻게 할지에 대한 처리와 각각의 테스트가 더 필요하다. 지금 필요한 것은 검토한 설명 하나를 저장하는 기능이어서 여기까지 범위를 넓히지 않았다.

## 결과

좋아진 점

- AI가 잘못 쓴 문장이 사람의 확인 없이 상품 정보가 되지 않는다.
- 초안을 생성한 뒤에도 DB의 설명이 그대로인지 `DescriptionReviewFlowIntegrationTest`로 확인한다.

감수한 점

- 초안은 서버에 남지 않는다. 저장하지 않고 넘어가면 다시 생성해야 한다.
- 이력이 없어서 다시 저장하면 이전 설명을 덮어쓴다.
- 검토 화면이 없어서 지금은 API 클라이언트(`api.http`)로 확인하고 저장한다.
